### 1.3 Priorities (the rules for every later change)
1. Frame rate first: an arcade racer must stay smooth.
2. No pop-in: nothing may appear, vanish or change look all at once in view. A cheaper setting that pops is worse than a dearer one that does not.
3. No hitches: no change in the middle of a race that makes new pipelines (things vanish while they are made, and the frame stutters).
4. Every change measurable on the user's machine (the log and the benchmark), and switchable off in Options > Graphics so it can be compared with `main`.

### 1.5 Diagnosis of the 1P Drop and Pop-In (to be confirmed by measuring)
- In one-player mode, the only change of the branch that alters the drawing was the trees' levels of detail: every tree's distance worked out each frame and its mesh swapped across a bound (Bevy extracts and batches it again), and the textured Meshy tree swapped for a vertex-painted lighter mesh at 60 m (the pop-in seen). It is now off by default.
- The shadows' pop-in was Bevy's: past the far bound of the last cascade it draws no shadow at all, so every shadow came in at once at 250 m. Fixed by the fade, at any level.
- Not yet measured on the user's machine with the new defaults. `make up` builds the game's own code at `opt-level = 1`; comparisons are fairer with `make build` on both branches.

### 1.6 Questions Asked and Answers Given
- **Dynamic antialiasing:** not built. Changing MSAA rebuilds every mesh pipeline; Bevy draws nothing whose pipeline is not ready, so things vanish for a few frames and the frame stutters at each change, worse than the edges it would save. Made a fixed option instead (MSAA 4×, FXAA, none).
- **Other settings lowered with the frame rate:** only the shadows, which change with no new pipeline (cascade count and distance are uniform data, the shadow map's size a texture). The grass, flowers and trees' distances were left out of the automatic levels: moving them in a race is a pop-in.
- **Shadows far away with less detail:** a first version pushed the last cascade to 500 m, coarse; dropped for the fade, which removes the pop at any distance without drawing more casters.
- **Dynamic resolution and FSR (recommended order, none built yet):**
  1. A render scale (for example 100, 85, 70, 50 %): draw the 3D at less than the window's pixels, scale it up with Bevy's contrast adaptive sharpening (the sharpening half of FSR 1), the interface at full resolution on top. The biggest win on Retina and scaled 4K Mac displays, where "Dynamic" resolution draws very many pixels (the log's `window=` shows how many). Changing the size makes no new pipeline, only textures, so it suits automatic control.
  2. Then a controller over that scale, as the shadows' one, to hold the target frame rate.
  3. FSR 1 (spatial, EASU and RCAS) ported to a shader, if scaling up with sharpening is not enough. FSR 2/3 (temporal) need motion vectors and jitter and have no Bevy integration; MetalFX is not reachable through wgpu.
  4. Other ideas: Bevy's experimental GPU occlusion culling (hills hide many trees), tree impostors (billboards) instead of lighter meshes far away (less pop), a draw-distance option.
  The note in Bevy 0.19: `MainPassResolutionOverride` only shrinks the main pass inside a full-size target for an upscaler (DLSS) to fill, so a render scale needs the 3D cameras to draw into a smaller texture shown over the window, split screen included.

### 1.7 How to Measure
- **The performance log** (Options > Graphics > Performance log, on by default; the path is printed when the game starts): `~/Library/Application Support/motorust/logs/perf-<unix time>.log` on macOS. A heading with the GPU, CPUs and system; then a line every 5 s, and at once when the screen, mode, players, pause, track, resolution, window or an option changes, so no line mixes two of them. Fields: `t`, `frames`, `seconds`, `fps`, `fps_1pct_low`, `ms_p50`, `ms_p95`, `ms_p99`, `ms_max`, `update_ms_p50`, `update_ms_p95` (the simulation's share of each frame: far below the frame time means the GPU or drawing holds it back), `cpu_process_pct`, `cpu_system_pct`, `mem_process_gib`, `mem_system_pct`, `entities`, and the context: `state`, `mode`, `players`, `paused`, `track`, `trees`, `lighter_far_trees`, `lighter_split_screen`, `shadows` (chosen/in use), `antialiasing`, `fps_limit`, `resolution`, `fullscreen`, `pipelined_rendering`, `frame_latency`, `window` (physical pixels @ scale factor), `ui_scale`, `tree_levels` (trees in sight drawn whole/lighter/lightest).
- **The benchmark:** `make bench` (`cargo run --release -- --bench`; or `MOTORUST_BENCH=1`). Free ride on autopilot, frame rate unlimited, eight scenarios per track: `1p` (shadows high, MSAA 4×, whole trees), `1p-shadows-medium`, `1p-shadows-low`, `1p-fxaa`, `1p-no-antialiasing`, `1p-lighter-far-trees`, `2p` (less detail), `2p-full-detail`. Each settles 4 s and is measured 10 s (`MOTORUST_BENCH_SECONDS`), on the tracks in `MOTORUST_BENCH_TRACKS` (as `0,2`) or all five (about 12 minutes). The table is printed and written to `bench-<unix time>.txt` beside the log; the game then closes. The window and resolution are the player's own, so run it at each resolution to compare; the settings it tries are never saved.
- **For a Claude session on the user's Mac:** from the repository, `make bench` (or `MOTORUST_BENCH_TRACKS=0 MOTORUST_BENCH_SECONDS=8 make bench` for a quick pass), then read the newest `bench-*.txt` and `perf-*.log` in `~/Library/Application Support/motorust/logs/`. Compare `1p` against the other 1P rows to see what each setting costs, `update_ms` against `ms_p50` in the log to tell CPU from GPU, and `2p` against `2p-full-detail` for the split screen's savings. To compare with `main`, which has neither the log nor the benchmark, play the same track on both builds (`make build`) with the options in the "Same as `main`" column above and compare the FPS counter, or the log's `1p` lines on this branch.

## 2. Stopping the Benchmark, Following It in the Terminal, Results per Machine (2026-10-16)

### 2.2 Implementation Details
- No alias: `make bench` stays the command (a `test.performance` alias was added and taken out again at the user's word). Its help line says Esc stops it.
- **In the terminal** (`src/bench.rs`, plain lines, apart from the game's log): first the machine (`motorust <version> benchmark on <machine>`; the system, CPU and cores, memory, from Bevy's `SystemInfo`; the GPU, backend and driver; the window's pixels and scale factor, the resolution option and fullscreen; the trees, pipelined rendering and frames queued), how many scenarios, how long each and about how long in all, where the results go and that Esc stops it. Then, for each scenario, `[ n/N] track · scenario`: "setting up the race" when a track or the players change, "settling 4 s, then measuring 10 s", and when measured its figures: fps, slowest 1 %, the frame time at the middle and at 95 %, the simulation's time at the middle (`FrameStart::elapsed`, the same measure as the log's `update_ms`) and the game's CPU (Bevy's sysinfo reading, as a share of all the cores), with about how many minutes are left. At the end, the whole table and where it is written.
- **Where the results go:** `bench-results/` in the folder it is run from (the repository with `make bench`; if it cannot be made there, beside the performance log). One file for each run, named after when it began (UTC, `stamp`: `2026-10-16_1830`) and the machine's name (`hostname`, made fit for a file name by `file_name`: `joshuas-mac-mini`), e.g. `2026-10-16_1830_joshuas-mac-mini.txt`: its heading is the machine's lines (as `#` comments), then the table's heading, each scenario's line written and flushed as soon as it is measured (track, scenario, fps, 1 % low, p50 ms, p95 ms, sim ms, cpu %), and `# finished` or `# stopped after N of M`. The run's performance log goes beside it (`<same name>.perf.log`, through `PerfLog::to`). Runs on several machines sit side by side, to be committed and pushed, and read from the branch. (This replaces section 1.7's `bench-<unix time>.txt` beside the performance log.)
- **Stopping:** Esc writes `# stopped after N of M`, prints the table so far and closes; closing the window or Ctrl+C keep every scenario already written.
- A file left in the repository by a crash during a benchmark run here (`motorust-crash.log`, committed by mistake in `92f0579` and removed by the user's `c4332b4`) is now ignored by git.
