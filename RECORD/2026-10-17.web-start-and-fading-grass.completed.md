# The Web Version Quit Before It Showed

## 1. Grass, Flowers and Petals Fading Out on WebGL2 (2026-10-17)

### 1.1 User Request
> "En web no llega a arrancar" (the web version does not start), with the browser's console: on WebGL2 (ANGLE over Metal, Apple M4 Pro), `Caught rendering error: Validation Error ... In Device::create_render_pipeline, label = 'pbr_opaque_mesh_pipeline' ... Shader global ResourceBinding { group: 0, binding: 14 } is not available in the pipeline layout ... Buffer structure size 1024, added to one element of an unbound array, if it's the last field, ended up greater than the given min_binding_size, which is 16`, then `Quitting the application due to Validation RenderError`.

### 1.2 Implementation Details
- **Cause** (Bevy 0.19.1, and still so in 0.20.0): group 0, binding 14 of the mesh view is the table of `VisibilityRange`s (`visibility_ranges`), which only the vertex shader of a mesh that fades out reads (`VISIBILITY_RANGE_DITHER`, set for an entity whose range has a margin). With fewer than six storage buffers (WebGL2) the shader declares it as a uniform `array<vec4<f32>, 64>` (1024 bytes) and Bevy fills it with exactly 64, but its bind group layout (`bevy_pbr/src/render/mesh_view_bindings.rs`) gives it `min_binding_size` of `Vec4::min_size()` (16 bytes), right only for the storage buffer of the desktop. wgpu refuses every pipeline that fades, and the game quits on the first frame that draws one. The grass (tufts and ragged edges, `src/world/tufts.rs`), the flowers (`src/world/flowers.rs`) and the petals (`src/world/japan.rs`) all fade out at the end of their reach, since `bde4639` (2026-10-14).
- **Fix** (`src/world/detail.rs`): one `fading_out(reach, fade, use_aabb)` builds the range of all three. On the desktop it is as before (`reach..reach + fade`); on the web (`settings::WEB`) it ends at once, halfway through the fade, so as far on average and with no margin: no pipeline dithers, and none reads binding 14. `shortened` (two players) keeps it abrupt. The rest of Bevy's layout cannot be changed from the game, and forking `bevy_pbr` for one line was not worth it.
- **Docs:** `docs/building.md` (What changes in the browser) and `docs/architecture.md` (`src/world/detail.rs`).

### 1.3 Verification & Testing
- Reproduced here: the web build (`wasm32-unknown-unknown`, release with `lto = false` and 16 codegen units to build quicker, `wasm-bindgen` 0.2.129) served locally and opened in headless Chromium with WebGL2 over SwiftShader (a temporary Playwright harness, not committed, pressing "Jugar online" and reading the console). Before the fix: the same `pbr_opaque_mesh_pipeline` error at group 0, binding 14 (1024 against 16 bytes) and "Quitting the application due to Validation RenderError". After it: no rendering error, the page at `data-motorust="ready"` and the welcome screen drawn over Bahía GP, its grass and trees in place; only Bevy's usual WebGL2 warnings (no SSAO, OIT, atmosphere; one shadow cascade). Not driven on into a race there (software rendering is too slow for it); every range that faded goes through `fading_out`.
- New test: `what_fades_out_ends_at_once_on_the_web` (as before on the desktop; on the web abrupt, halfway through the fade, and so after `shortened`).
- `cargo test`: 540 passed, 1 ignored (the test count in `docs/architecture.md`: 545, 541 off macOS). `cargo fmt --check` clean; `cargo clippy --all-targets -- -D warnings` clean. The wasm build's only warnings are the five about `src/perf_log.rs` items unused on the web, as before.
