## 2. Trees: One Solid Mesh Each, No Pop-In

### 2.1 User Request
> "ahora estoy en 100~110 fps, además, los árboles tienen un efecto pop-in muy acusado / simplificaría su diseño"

### 2.2 Implementation Details
- **Cause of the pop-in:** up close every tree was three entities: its wood with a dark core of its crowns, its alpha-masked leaf cards, and beyond 70 m (cross-fading over 12 m with `VisibilityRange`) a solid model with bigger, lighter crowns. The swap between the two looks was visible as each tree crossed 70 m.
- **Cost:** the leaf cards were hundreds of alpha-tested quads per tree within 70 m, and they also cast shadows into every cascade with the alpha test. On a tile-based GPU (Apple M1) alpha testing defeats hidden-surface removal, so this was the most expensive thing the branch had added.
- **Now (`src/world/props.rs`):** as on `main`, each tree is one opaque mesh (`merged_variant`: its wood painted bark and its crowns painted in their vertices), one entity, the same near and far, batched with the other trees of its variant. `TreeMeshes`, `leaf_cards`, `TREE_NEAR`/`TREE_FADE`, `FAR_CROWN`, `CROWN_CORE`/`CORE_SHADE`, `LEAF_*` and the species' `needles`/`foliage` fields are gone.
- **Crowns** stay at `ico(2)` (162 vertices before shaping, `main` used `ico(3)` with 642): their lumpy shaping looks the same in screenshots, and with thousands of trees drawn into the view and the shadow cascades it is a quarter of the triangles.
- **Textures (`src/world/foliage.rs`, `src/world/textures.rs`):** the leaves/needles texture (`foliage::leaves`, `BROAD_LEAVES`, `NEEDLES`, `Canvas::leaf`) and `WorldTextures::leaves` are removed.

### 2.3 Verification
- `cargo test`: 332 passed (the leaf-card test is replaced by `each_tree_is_one_solid_mesh_of_bark_and_foliage`; the masked-mipmap coverage test now uses the tuft texture). `cargo fmt --check` and `cargo clippy --all-targets` clean.
- Screenshots on Turbo Bay at three spots (pines, cypresses, almonds, broadleaves; from 5 m to the horizon): one look at every distance.
- lavapipe, same views (ms/frame, lower is better; CPU rasteriser, so only a rough guide for an M1):

  | View | Leaf cards (before) | Solid, `ico(3)` | Solid, `ico(2)` (kept) |

## 3. Input Latency First

### 3.1 User Request
The user shared a guide, "Motorust: Input Latency First, Dynamic Quality Second" (priorities: 1. input lag, 2. performance), and asked to take it into account: disable pipelined rendering, choose the present mode carefully, set `desired_maximum_frame_latency = 1`, sample input as late as possible, a frame-time-driven dynamic resolution controller (`MainPassResolutionOverride`), an FPS limiter below what the GPU sustains, upscalers (DLSS/FSR) last.

### 3.2 Implementation Details
- **Pipelined rendering off (`src/main.rs`):** `PipelinedRenderingPlugin` is disabled on the desktop (it is not in Bevy's default plugins on the web). Each frame is now extracted and drawn right after it is simulated from the controls just read, instead of on the render thread while the next frame is simulated: about one frame less of latency, at the cost of throughput when the CPU is the bottleneck.
- **One frame queued (`src/settings.rs`):** the window asks for `desired_maximum_frame_latency = 1` (`FRAMES_QUEUED`), Bevy's default being 2, so the frame on screen is never two frames behind the controls.
- **Present mode:** unchanged. "Screen" stays `AutoVsync` (FifoRelaxed, else Fifo): Bevy's `Mailbox` falls back to `Immediate` where Mailbox is missing (Metal on macOS has only Fifo and Immediate), which would tear; with one frame queued, Fifo adds little. "Unlimited" stays `AutoNoVsync` (Immediate first) for the lowest latency with tearing.
- **Frame limiter moved to after presenting:** with a fixed cap, the wait used to happen in the main world's `Last`, between reading the controls and drawing the frame, so the frame showed controls that much older. Now `cap_frames` copies the cap into `FrameCap`, extracted to the render world (`ExtractResourcePlugin`), and `limit_frames` runs in the render world's `RenderSystems::PostCleanup`, after `render_system` has presented: the next frame starts right after the wait, with fresh controls.
- **Input sampling:** already as late as practical: gamepads are polled in `PreUpdate` before Bevy's input systems, and the player's controls are turned into `BikeInput` in `RunFixedMainLoopSystems::BeforeFixedMainLoop`, right before the fixed steps of the same frame; rendering interpolates between fixed steps (120 Hz), so no frame waits for the next tick.
- **Not done (yet):** dynamic resolution. In Bevy 0.19 `MainPassResolutionOverride` only shrinks the main pass viewport inside the full-size target, for an upscaler (DLSS) to fill; without one the picture would sit in a corner. A working version needs the 3D cameras to draw into a smaller texture that is scaled up before the UI, split screen included: a separate piece of work. DLSS (NVIDIA only) and FSR (no integration) are out of scope for an M1.

### 3.3 Verification
- `cargo test`: 332 passed (`a_fixed_limit_holds_the_frames_back` now runs `cap_frames` then `limit_frames` and still sees ≥ 98 ms over six 50 fps frames). `cargo fmt --check` and `cargo clippy --all-targets` clean.
- The game starts and renders with pipelined rendering disabled (lavapipe, Turbo Bay at 40 m/s: 771 ms/frame against 733 with it, the expected small loss of overlap on a CPU rasteriser). Latency itself cannot be measured here; the user is to compare on the M1 Pro.

## 4. Circuits Prepared on Their Own Thread (Fix for Section 3)

### 4.1 Problem
Found while taking screenshots of the track screen: with pipelined rendering off, nothing new was drawn there for ~430 frames (about 25 s on the 4-core test machine; seconds on an M1), and then everything caught up at once. Entering the track screen starts preparing every other circuit in the background (`cache_all_circuits`), and those tasks ran on Bevy's `AsyncComputeTaskPool` (1 thread on 4 cores, 2-3 on an M1 Pro). Bevy 0.19 compiles render pipelines on that same pool (`PipelineCache` → `create_pipeline_task`), so the pipelines the screen needed queued behind seconds of circuit work. Pipelined rendering had hidden it.

### 4.2 Implementation Details
- **`src/world/mod.rs`:** `circuit_pool()` is a dedicated one-thread `TaskPool` ("Circuits", built once in a `OnceLock`), and `cache_all_circuits` spawns the preparations there. `Preparing` still holds `Task<Prepared>`, so `spawn_prepared_circuit` (`poll_once`) and `rebuild_world` (`block_on` when a circuit is needed now) are unchanged. Each preparation still spreads its terrain over `Urgency::Background` threads. On the web the pool is Bevy's single-threaded one, as before.

### 4.3 Verification
- Track screen screenshots at frames 30 and 60 now save and the frame time is that of a drawn frame (lavapipe ~1 s), where before no frame was presented until the circuits were ready.
- `cargo test world::` (76 passed), `cargo fmt --check`, `cargo clippy --all-targets` clean on the fix alone.
