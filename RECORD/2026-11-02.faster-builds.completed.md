# Faster Builds, and the Engine at v0.0.19 (2026-11-02)

## 1. Bevy Linked Dynamically for `make up`, PRs Only Checked, the Engine at v0.0.19

### 1.1 User Request
> Asked whether the engine could also make "a pseudo-binary, like a DLL" to simplify the game's builds. Answered no: Rust has no stable binary interface (a DLL of the engine would serve only a game built with the very same rustc, Bevy, features and flags), most of Bevy is generic and generated in the crate using it, a single executable would become several, the web has no DLLs, and a C interface would cut through the themes and plugins. The engine at a fixed tag is already cached compiled by the CI as a dependency. Proposed instead: (1) Bevy linked dynamically for `make up` only; (2) a PR's CI only checking each system, full builds on `main` and releases. Also found: PR #33's run 171 failed on a check too tight for a busy runner, fixed in the engine. "Sí, haz 1 y 2, y lanza tú la release" (yes, do 1 and 2, and run the release yourself).

### 1.2 Implementation Details
- **The engine at v0.0.19**: the check `circuits_are_prepared_in_the_menus_and_let_go_for_a_race_on` gave up after 120 s, and on GitHub's runner, every test running at once, the game's eight circuits took longer ("the circuits never arrive", run 171 of PR #33). Fixed in the engine (`080e4b5`, a 600 s bound: what it checks is that they arrive; the engine's `RECORD/2026-11-02.slow-runners.completed.md`); its `release.yml` run by Claude (`patch`, run 41394897668, 20 min), giving **v0.0.19** (`e17e3f0`). `Cargo.toml` takes it in both places, `cargo update -p motorust-engine`.
- **(1) `make up` with Bevy linked dynamically**: the game's feature `dynamic` (`bevy/dynamic_linking`, `Cargo.toml`); `make up` is `cargo run --features dynamic`. `src/main.rs` refuses the feature in a release build (`compile_error!` without `debug_assertions`): such an executable needs `libbevy_dylib` beside it, which no package carries. `Cargo.lock` gains `bevy_dylib`. No linker settings: Rust links with LLD on Linux x86_64 already (since 1.90), and macOS's linker is fast.
- **(2) A PR's CI** (`.github/workflows/build.yml`): after the tests, each desktop target and the web are only checked in a PR (`cargo check --target <target>`, `cargo xwin check` when Windows is cross-built; no code generated), with no wasm-bindgen, packaging or artifacts; pushes to `main`, runs by hand and the release's calls build and package as before (`github.event_name` is the caller's, `workflow_dispatch`, when `release.yml` calls it). On every run, every system checks that `tools/engine_dir.sh` finds the engine's credits, so a PR tries it on Windows (`cygpath`) and macOS too.
- **Docs**: `docs/building.md` (`make up` and how it links, the measures; `build.yml` in a PR).

### 1.3 Verification & Testing
- The first `cargo build --features dynamic`: 15.5 min (all of Bevy again, as a shared library). Then, after touching `src/game/mod.rs`: **2.1 s** linked dynamically against **6.9 to 10.9 s** statically; going from one to the other recompiled only the game (1 crate), both builds kept in `target/`.
- `cargo run --features dynamic` loads `libbevy_dylib` and runs up to the window (here there is no display: winit's "neither WAYLAND_DISPLAY nor ... DISPLAY is set"); the crash report wrote its file, as it should.
- The guard: `rustc` on `src/main.rs`'s lines with `feature="dynamic"` and no debug assertions fails with its message; with debug assertions, or without the feature, compiles.
- The workflow parsed as YAML, each step's condition listed.
- With the engine at v0.0.19: `cargo fmt --all --check`, `cargo clippy --all-targets -- -D warnings` clean; `cargo test`: 234 passed, 1 ignored.
